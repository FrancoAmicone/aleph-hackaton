● Confirmado y con evidencia. Te lo separo, porque hay dos cosas distintas
  metidas en la misma pregunta.

  Estado actual: no pasó nada

  La key que generé (pear://gisx7sp6...) no quedó seteada en ningún lado.
  package.json del spike sigue con el placeholder pear://<YOUR_KEY_HERE>. pear 
  touch sólo imprime la key; no la escribe ni la publica. Es descartable — la
  usé sólo para desbloquear el crash del worker. Tenías razón igual en frenarme.

  Qué es la key

  pear touch genera un par de claves. El pear://<key> que ves es la parte
  pública: es la identidad de la app y a la vez su dirección de distribución. No
  es un nombre que registrás en un servidor — no hay servidor.

  La parte privada es la que autoriza a publicar. Verifiqué dónde vive:
  ~/.config/pear (122MB de corestores y db en esta máquina). O sea: local, fuera
  del repo, no se commitea, no se sincroniza con nadie.

  Por qué una sola key (el motivo real)

  Esto es lo que hace caro el error. Del flujo en docs/03-deploy-ota.md:

  npm pkg set upgrade=pear://KEY   # queda en package.json
  npm run make                     # el binario se buildea CON esa key adentro

  El upgrade link queda horneado en el binario. Una v1 instalada busca updates
  en pear://A y sólo en pear://A, para siempre. Si mañana alguien publica la v2
  en pear://B, esa v1 nunca se entera. No hay redirect, no hay alias, no hay
  forma de migrar a un usuario ya instalado.

  Y eso rompe exactamente el punto 4 del track: "demostrar un update OTA P2P en 
  vivo". Si el juez instala desde la key de uno y otro publica la v2 desde la
  suya, la demo no pasa — y es el criterio con más peso.

  Qué es seedear

  Como es P2P, no hay un servidor de donde bajar. Son dos pasos distintos:

  - pear stage pear://KEY <dir> — escribe tu código en un hypercore (log
    append-only) firmado con la private key. Ese hypercore vive en tu disco.
  - pear seed pear://KEY — anuncia ese contenido en el DHT y sirve los bloques a
    quien los pida.

  Sin seed, la key existe pero no hay de dónde bajar. Es un torrent sin seeders.
  Por eso docs/02-pear-cli.md lo marca en negrita: "Tiene que estar corriendo 
  para que otros instalen", y el track exige seeding activo durante todo el 
  juzgado.

  Lo que esto implica para el equipo

  El punto que no es obvio: sólo la máquina con la private key puede publicar la
  v2. Como vive en ~/.config/pear y no viaja por el repo, quien genere la key
  queda como único release manager. Si esa persona se queda sin batería a las
  12:50 del domingo, no hay demo de OTA.

  Mi recomendación: generar la key del proyecto una sola vez, en la máquina de 
  quien vaya a estar seguro presente y despierto durante el juzgado, y esa
  persona corre stage y seed. El resto instala y consume. Commitear el pear://
  público en el README (es público, no es secreto).

  No verificado — te lo marco explícitamente: si una segunda máquina sin la
  private key puede re-seedear el contenido para redundancia.
  docs/03-deploy-ota.md lo sugiere pero está marcado [NUESTRO], o sea es
  criterio del equipo, no doc oficial. Vale la pena probarlo cuando armemos el
  pipeline real, porque de eso depende el plan B de disponibilidad.

  Qué es ed25519

  Es el nombre de un algoritmo de firma digital. Se desglosa así:

  - ed = Edwards, por el tipo de curva elíptica que usa (curvas de Edwards).
  - 25519 = viene del número primo 2²⁵⁵ − 19.

  Ese primo define el "campo numérico" donde vive la curva — el universo de
  números con el que hace toda la matemática. No es un número arbitrario: se
  eligió porque está muy cerca de una potencia de 2, lo que permite
  implementarlo rápido y sin ramificaciones condicionales. Eso último importa
  por seguridad: un algoritmo que tarda distinto según la clave filtra
  información por el tiempo que tarda (timing attacks). Con 25519 eso no pasa.

  Por qué se repite en los dos lugares

  No es una coincidencia ni un requisito raro, son dos usos distintos del mismo
  nombre:

  ssh-keygen -t ed25519          # -t = TIPO de clave a generar
  cat ~/.ssh/id_ed25519.pub      # el archivo se llama así POR ese tipo

  ssh-keygen nombra el archivo según el algoritmo que usaste. Si hubieras puesto
  -t rsa, tendrías id_rsa y id_rsa.pub. Se repite porque elegís el tipo y
  después leés el archivo que ese tipo generó.

  Qué hace realmente

  Genera dos archivos:

  ┌────────────────┬───────────────┬──────────────────────────┐
  │    Archivo     │    Qué es     │         Dónde va         │
  ├────────────────┼───────────────┼──────────────────────────┤
  │ id_ed25519     │ clave privada │ nunca sale de tu máquina │
  ├────────────────┼───────────────┼──────────────────────────┤
  │ id_ed25519.pub │ clave pública │ la pegás en GitHub       │
  └────────────────┴───────────────┴──────────────────────────┘

  Cuando hacés git push, GitHub te manda un desafío matemático que sólo se puede
  resolver teniendo la privada. Vos lo resolvés, GitHub lo verifica con la
  pública que le diste. Nunca viaja una contraseña. Por eso es más seguro que un
  token: no hay nada que robar en tránsito.

  El gancho: ya entendiste esto hoy

  Es exactamente el mismo mecanismo que la key de pear:// que discutimos:

  ┌───────────────┬───────────────────┬─────────────────────────────┐
  │               │        SSH        │            Pear             │
  ├───────────────┼───────────────────┼─────────────────────────────┤
  │ Clave pública │ la subís a GitHub │ es el pear://gisx7sp6...    │
  ├───────────────┼───────────────────┼─────────────────────────────┤
  │ Clave privada │ ~/.ssh/id_ed25519 │ vive en ~/.config/pear      │
  ├───────────────┼───────────────────┼─────────────────────────────┤
  │ Qué autoriza  │ pushear al repo   │ publicar la v2 (pear stage) │
  └───────────────┴───────────────────┴─────────────────────────────┘
