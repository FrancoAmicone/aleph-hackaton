## Qué usar

| Necesito | Uso |
|---|---|
| Conectar 2 peers por public key (hole punching) | **HyperDHT** |
| Descubrir muchos peers en un "topic" y mantener conexiones | **Hyperswarm** |
| Log append-only persistente y replicable | **Hypercore** |
| Manejar muchos cores nombrados y co-replicarlos | **Corestore** |
| Base de datos key-value append-only compartida | **Hyperbee** |
| Filesystem P2P | **Hyperdrive** |
| Bytes / hex (no hay `Buffer` en Bare) | **b4a** |
| Generar keys, hashear topics | **hypercore-crypto** |

**[NUESTRO] Para un juego de terminal:** Hyperswarm alcanza. Un topic = una sala. Los mensajes
son efímeros (solo mientras los peers están online), que es exactamente lo que querés en una partida.
Solo agregar Hypercore/Hyperbee si hace falta persistir (leaderboard, historial, replay).

## Hyperswarm — el patrón base

Setup:

```bash
mkdir peer-app
cd peer-app
npm init -y
npm pkg set type="module"
npm install hyperswarm hypercore-crypto b4a bare-process
```

`peer-app/index.js`:

```javascript
import Hyperswarm from 'hyperswarm'
import crypto from 'hypercore-crypto'
import b4a from 'b4a'
import process from 'bare-process'

const swarm = new Hyperswarm()
const name = b4a.toString(swarm.keyPair.publicKey, 'hex')
process.once('SIGINT', () => swarm.destroy().then(() => process.exit(0)))

// Trackear todas las conexiones y loguear lo que llega
const conns = []
swarm.on('connection', conn => {
  const peer = b4a.toString(conn.remotePublicKey, 'hex')
  console.log('* got a connection from:', peer, '*')
  conns.push(conn)
  conn.once('close', () => conns.splice(conns.indexOf(conn), 1))
  conn.on('data', data => console.log(`${peer}: ${data}`))
  conn.on('error', e => console.log(`Connection error: ${e}`))
})

// Broadcastear stdin a todas las conexiones
process.stdin.on('data', d => {
  console.log(`${name}: ${d}`)
  for (const conn of conns) {
    conn.write(d)
  }
})

// Unirse a un topic común
const topic = Bare.argv[2] ? b4a.from(Bare.argv[2], 'hex') : crypto.randomBytes(32)
const discovery = swarm.join(topic, { client: true, server: true })

// flushed() resuelve cuando el topic fue anunciado del todo al DHT
discovery.flushed().then(() => {
  console.log('joined topic:', b4a.toString(topic, 'hex'))
})
```

Correr:

```bash
bare peer-app                        # primer peer, imprime el topic
bare peer-app <TOPIC_HEX_STRING>     # peers siguientes, pegan el topic
```

### Puntos clave

- **Una sola instancia de swarm por aplicación** — deduplica conexiones entre múltiples topics.
- El swarm maneja el discovery solo; no hace falta designar servidor/cliente explícitamente.
- **Conexiones efímeras:** los mensajes solo existen mientras los peers están online.
- `conn` es un stream duplex: `conn.write(...)`, `conn.on('data', ...)`.
- El topic es de **32 bytes**. Para salas con nombre legible: hashear el nombre.

### Topic desde un nombre de sala — ✅ VERIFICADO (spike 2)

```javascript
const topic = crypto.data(b4a.from('mi-sala-de-juego'))  // 32 bytes determinístico
```

Probado con `hypercore-crypto@3.7.0` sobre Bare: devuelve **32 bytes**, el mismo nombre da
siempre el mismo topic, y nombres distintos dan topics distintos. Así dos jugadores que tipean
el mismo nombre de sala caen en el mismo topic sin copiar hex.

### Teardown correcto — importa

```javascript
process.once('SIGINT', () => swarm.destroy().then(() => process.exit(0)))
```

Si el swarm no se destruye en el teardown, quedan registros colgados en el HyperDHT y las
próximas conexiones tardan más. Ver `06-troubleshooting.md`.

**Además** hay que limpiar los timers propios (`clearInterval` del game loop). Un interval vivo
mantiene el loop de Bare y el proceso queda colgado aunque el swarm ya esté destruido.
Verificado en los spikes 1 y 2.

## Lecciones del spike 2 — leer antes de escribir código de red

Todo lo de esta sección está **verificado empíricamente**. Ver `spikes/02-hyperswarm/SPIKE.md`.

### 1. Hacen falta DOS handlers de error, no uno

El bug más caro del spike. Con sólo `conn.on('error')`, cuando un peer se cae el otro **muere**:

```
Uncaught Error: connection reset by peer
    at FramedStream._destroy (streamx/index.js:725:5)
```

El `ECONNRESET` se propaga por el stream que envuelve al `conn` (`FramedStream`), no sólo por
el `conn`. Traducido: **un jugador cierra la ventana y al otro se le cae el juego.**

```javascript
conn.on('error', (err) => { ... })
framed.on('error', (err) => { ... })   // ESTE es el que falta siempre
```

### 2. Una caída abrupta NO se detecta sola

Hyperswarm va sobre **UDX (UDP)**: no hay `RST` de TCP que avise.

| Cómo se fue el peer | Se detecta |
|---|---|
| Cierre ordenado (`swarm.destroy()`) | **Inmediato** — llega `connection reset by peer` y `close` |
| Caída abrupta (`kill -9`, batería, cable) | **NO llegó nada en 10s** |

**[NUESTRO]** Para un juego en tiempo real hace falta un **heartbeat de aplicación**: ping cada
2s, y dar por muerto al peer que no dio señales en ~6s. Medido: detección en ~7s. El tick del
ping sirve de game tick.

### 3. Los mensajes JSON necesitan framing

Los streams duplex **no preservan límites de mensaje**: dos JSON seguidos pueden llegar pegados
en un chunk o partidos al medio, y `JSON.parse` revienta. Usar **`framed-stream`** (ya es
dependencia del template): prefija cada mensaje con su longitud → 1 write = 1 `data`.

### 4. La public key del peer cambia en cada arranque

`new Hyperswarm()` genera un keyPair nuevo cada vez. El mismo jugador que se reconecta aparece
con **otra public key**.

**[NUESTRO]** Si el juego necesita identidad persistente (puntaje, "es el mismo que volvió"),
hay que guardar el keyPair en disco y pasárselo al swarm.

### 5. Reconexión automática

Matando un peer y relanzándolo, Hyperswarm los volvió a conectar solo en ~7s mientras el topic
siguiera joined. No hay que hacer nada.

### 6. ⚠️ El discovery NO es confiable al primer intento — MEDIDO

Dos peers en la **misma máquina**, 10 corridas por escenario, topic nuevo cada vez:

| Teardown de la corrida anterior | Conectaron | Tiempo cuando conectó |
|---|---|---|
| Sucio (`kill -9`, sin `swarm.destroy()`) | **4 / 10** | siempre 7s |
| Limpio (SIGINT → `await swarm.destroy()`) | **7 / 10** | 7s (una vez 10s) |

Dos conclusiones:

**a) El teardown sucio casi duplica los fallos** (40% → 70% de éxito). Confirma
empíricamente lo que dice `06-troubleshooting.md`: los swarms que no se destruyen dejan
registros colgados en el HyperDHT y degradan las conexiones siguientes. **`await swarm.destroy()`
no es prolijidad, es funcionalidad.**

**b) Aún con teardown limpio, 3 de 10 no conectan.** Y no es que tarden: el timeout era de 40s
y los éxitos siempre llegaron a los ~7s. O entra en la ventana de reanuncio del DHT, o no entra.

**[NUESTRO] Consecuencia de diseño para el juego:** hace falta un **retry** — si no apareció
nadie en ~10-15s, hacer `swarm.leave(topic)` + `swarm.join(topic)` y reintentar, mostrando
"buscando jugadores..." en pantalla. Con 70% por intento, tres intentos dan ~97%.
**Nunca asumir que el primer join encuentra al otro jugador.**

**Contexto que baja la alarma:** los dos peers corrían en la misma máquina, o sea el mismo NAT
— el caso de hairpinning más difícil que existe. La doc oficial ya lo advierte
(`06-troubleshooting.md`: *"Dos máquinas en la misma red NAT a veces no se ven"*).
**Pendiente de medir entre dos máquinas distintas**, que es el escenario real de la demo.

## P2P no es "sin internet" — para encontrarse hace falta red

HyperDHT arranca con bootstrap nodes hardcodeados en IPs públicas:

```
88.99.3.86@node1.hyperdht.org:49737
142.93.90.113@node2.hyperdht.org:49737
138.68.147.8@node3.hyperdht.org:49737
```

Y **Hyperswarm no tiene mDNS ni descubrimiento de LAN** (verificado por grep en el paquete).
Sin llegar a esos nodos, dos peers **no se encuentran** aunque estén en el mismo wifi.

### Pero una vez conectados, el DHT ya no hace falta — ✅ MEDIDO

Bloqueando UDP saliente hacia internet durante 30s con dos peers ya conectados:
**15 de 15 ticks respondidos, cero mensajes perdidos, ningún peer dado por muerto.**

El DHT sirve para **encontrarse**, no para **hablar**. Una vez hecho el hole punching el
tráfico va directo peer a peer.

| Situación | ¿Sobrevive al corte de internet? |
|---|---|
| Los dos en la **misma LAN** (mismo wifi del evento) | Sí — el tráfico es LAN, no toca internet |
| En **redes distintas** (hole punching por IPs públicas) | No — ahí el tráfico sí va por internet |

**Para el juzgado:** si el wifi del evento sigue en pie pero pierde internet, con los jugadores
ya dentro de la partida, la partida sigue. Lo que no sobrevive es que se caiga el wifi entero.

Reproducir con `spikes/02-hyperswarm/test-sin-internet.sh` (necesita root).

## Storage y replicación

Tres guías oficiales bajo *Store and replicate*:

1. **Replicate and persist with Hypercore** — persistir mensajes y streams con replicación
   append-only. https://docs.pears.com/how-to/store-and-replicate/
2. **Work with many Hypercores using Corestore** — manejar y co-replicar muchos cores nombrados
   desde un solo Corestore.
3. **Share append-only databases with Hyperbee** — peers writer y reader con Hyperbee,
   Corestore y Hyperswarm.

En el template, el Corestore vive en `path.join(dir, 'pear-runtime', 'corestore')` y `pear.storage`
da el path de storage de la app. Se le puede pasar un `store` y un `swarm` ya existentes al
constructor de `PearRuntime` para compartir la misma instancia entre el updater y la app
(así lo hace `variant/single-thread`) — **esto evita tener dos swarms compitiendo.**
